# Mac smoke results — 2026-10-06

**Native integration works on this Mac; no iPhone or production qualification is implied.** This is a small smoke test, not a benchmark or quality ranking. The next gate remains a separate physical-iPhone harness, not a shipping Download button.

## Configuration

- Apple M2, 16 GiB physical memory, macOS 26.6.1 (25G76), Swift 6.3.3.
- Release build of the standalone Swift harness, llama.cpp b11429, publisher Qwen3-0.6B Q8_0. Exact verified identities are in [artifacts.json](artifacts.json).
- Native logs identify Metal device Apple M2 and layer offload. Requested GPU layers: 99; 128-token prefill batches; non-thinking single-turn template; seed 42, top-k 20/top-p 0.8/temperature 0.7.
- Output cap 128 for these probes (the harness accepts up to 512). Two configured contexts, 2,048 and 4,096 tokens. This does **not** exercise 4K near-full input or sustained 512-token output.
- Four Swift tests passed: native template framing, control-marker/oversize rejection, bounded experiment options, missing artifact rejection. Release build completed successfully.

MB above is decimal. Native model-load times after initial warm-up were 0.235–0.376 seconds, excluding full-file SHA verification. First-token/elapsed measurements include context creation and prefill, but exclude model loading/hash verification and final deferred resource cleanup. Dividing total output by elapsed yields roughly 45–54 tokens/second for the tiny warm 2K/4K samples; this is **not decode-only throughput**.

Process-lifetime peak RSS reached approximately **1.65 GB** in later probes, distinct from sampled physical footprint. It includes model verification and any earlier allocations in that process. Neither measurement is an iPhone peak-memory guarantee or a recommended admission threshold.

The first 2K run was much slower: model load 38.62 seconds, generation approximately 10.8 seconds per repeat, first-token 1.63/0.64 seconds. That run was also a release build, not a debug build, and overlapped compiler/test activity and first Metal initialization. Its cause was not isolated. Preserve it as a startup/system-contention observation; do not infer that 4K is faster than 2K or present the initial 11-second value as representative warm performance. The later like-for-like 2K rerun produced the same 33-token text in approximately **0.71 seconds**.

## Limits that remain material

- Thermal state was `fair` (1) at the end of every probe. No controlled power state, battery drain, energy, ambient temperature, sustained thermal test, or independent repeated cold-boot study was performed. This Mac was doing other work during part of the run.
- Tokenization is native and covers the actual complete template; identical input token hashes across runs are a consistency check, not independent Transformers/tokenizer parity certification.
- Cancellation was deliberately requested between tokens. Its sub-microsecond observation is merely a control-flow check before cleanup, **not** in-flight Metal abort, GPU synchronization, resource-release, backgrounding, or end-to-end UI Stop latency. The native abort callback is CPU-only according to the pinned header.
- The factual prompt is General-mode restatement, not Sekret Knowledge Base retrieval/citation/verification. One correct condition and one missing Korean instruction do not establish broad quality. The latter is a directly observed instruction-following limitation.
- No supported-phone tier, maximum safe context, verified installer, app model switching, grounded-answer capability or production model catalogue entry was established.
